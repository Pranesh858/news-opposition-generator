# Category-Aware News Sentiment & Opposition Opinion Generator

Accepts a news headline or short article, detects whether it's **Politics**
or **Sports**, classifies its sentiment, and generates a respectful,
non-inflammatory **opposing viewpoint** to encourage balanced thinking.

## Architecture

```
frontend/  React (Vite) — input box + results display
backend/   FastAPI      — /analyze endpoint, calls Groq's free LLM API
```

The frontend never talks to the LLM directly — everything goes through
the backend, so the API key stays server-side and every request passes
through the safety filter before it reaches the model.

## Setup

### Backend
```bash
cd backend
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# edit .env and paste a free key from https://console.groq.com/keys
uvicorn main:app --reload --port 8000
```

### Frontend
```bash
cd frontend
npm install
npm run dev
```
Open the URL Vite prints (usually `http://localhost:5173`).

## How the opposition logic works

Everything happens in **one LLM call** per request (see `SYSTEM_PROMPT` in
`backend/main.py`). The prompt asks the model to do three things in a
fixed order, and return strict JSON:

1. **Category** — forced to exactly `"Politics"` or `"Sports"`, no other
   labels allowed, so the frontend can always render a badge correctly.
2. **Sentiment** — `Positive` / `Negative` / `Neutral` plus a one-line
   reason, so the user isn't just told a label but *why*.
3. **Opposition opinion** — a short counter-viewpoint. This is the core
   of the project, so the prompt bakes in explicit rules:
   - Acknowledge the original article's validity first, then complicate it —
     this is what keeps it from reading like a rebuttal/attack.
   - No insults, no attacking a person's character, no slurs.
   - For **Sports**, the "opposition" is framed as a rival-fan or
     alternate-analysis take (e.g., defending the losing side), not a
     political statement.
   - For **Politics**, the model is told to steelman the opposing policy
     argument rather than caricature it, and to avoid naming specific real
     politicians where possible — so the tool critiques *positions*, not
     *people*.
   - If there's genuinely no reasonable opposing take (e.g., a plain score
     report), the model is told to say so rather than invent one.

## Safety controls

Two layers, one **before** the model runs and one **built into the prompt**:

1. **Input filter** (`is_input_safe` in `main.py`) — a lightweight regex
   check that blocks obviously violent/hateful input *before* it's ever
   sent to the LLM. This is a first line of defense, not a complete
   moderation system — for production use you'd want a proper moderation
   API here.
2. **Prompt-level constraints** — the system prompt explicitly forbids
   insults, character attacks, and slurs, and requires the model to
   validate the original view before offering a counter-angle.
3. **Disclaimer** — every response includes a fixed disclaimer (not
   generated by the model, hardcoded in `SAFETY_DISCLAIMER`) clarifying
   that the output is an AI-generated alternative perspective, not a
   factual claim or a real person's opinion.

## API

`POST /analyze`
```json
{ "text": "Local council approves new stadium funding despite public opposition..." }
```

Response:
```json
{
  "category": "Sports",
  "sentiment": "Negative",
  "sentiment_reason": "The headline frames the funding decision as controversial.",
  "opposition_opinion": "...",
  "disclaimer": "This is an AI-generated alternative perspective..."
}
```

## Notes / things to extend for a fuller submission

- Swap the regex input filter for a real moderation endpoint if you want
  stronger safety guarantees.
- Add a small SQLite log of past analyses if your rubric wants persistence.
- The Groq free tier has rate limits — if you hit them during a demo,
  the `GROQ_MODEL` constant in `main.py` can be swapped to a smaller model.
